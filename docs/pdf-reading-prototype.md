# PDF 正文读取原型

版本：`0.15.0-preview.4`。前置的合成文本回传已在一套真实 ChatGPT + Secure MCP Tunnel 连接上连续成功两次。preview.3 的真实 PDF 已通过原文件校验，随后在 `extract` 阶段报告 `ASSET_UNAVAILABLE`；资源请求在失败提交后约 82 秒才到本地服务，服务器随后成功返回。本版内置解析需要的字体和 CMap，去掉该资源请求链路，并修复底层错误被吞掉的问题。真实 PDF 正文读取仍须复验。

## 使用方式

构建后正常重启隧道，更新 ChatGPT 的 WebCodex 工具定义，并在新对话启用该连接。直接要求「读取某工作区的某 PDF，并提炼重点」即可；模型应选择 `document_open`，随后用 `document_read` 获取正文。无需安装扩展、部署公网接口或逐个选择、上传、发送文件。

`document_open` 要求 `workspace_id`、工作区内相对 `path` 和 `expected_device_id`。首次自动准备第 1–3 页。`document_read` 使用返回的 `document_id` 和相同工作区、设备，可指定 `start_page`、`page_count`（最多 5 页）。`pending` 只表示尚在处理；只有 `ready` 才包含 `pages` 正文。按 `next_start_page` 继续读取任务需要的页数，报告实际覆盖范围。

组件需要保持挂载以继续解析后续页。模型按返回的 `retry_after_ms` 给组件执行时间，在 `pending_reads_remaining` 内取同一范围；不得打开阻塞等待工具或新文档绕过限额。超时或错误应报告实际状态。

已完整缓存的页可直接用于较小范围；如果页内容因总预算截断，则缩小范围会重新准备。组件一旦提交致命读取错误，该文档的所有范围立即返回同一错误，不再让其他页继续排队。`progress` 的轮询次数、已服务字节数等是服务端观察，不证明浏览器收到或校验成功。

失败时普通工具的 `error.details.component_diagnostics` 返回组件自报的版本、实际阶段、固定错误码和可选详情码；服务端进度仍单独保留。原文件校验细分编码、长度、分块与整文件摘要、结束位置等原因。资源失败的顶层错误仍可为 `ASSET_UNAVAILABLE`，诊断保留有限白名单中的底层错误码和详情；未知异常统一为 `UNKNOWN_ERROR`。不传原字节、路径、凭据或宿主原始错误消息。旧组件未提供诊断时不推断其版本或具体原因。

## 实际数据路径

1. 本地服务在授权工作区内捕获完整 PDF 快照，计算 SHA-256；公开工具只返回元数据，私有票据位于 `_meta`。
2. 组件通过私有 MCP 工具取得完整原字节，校验每块与整文件哈希。
3. 组件运行随构建捆绑的 PDF.js `6.3.289`，从完整字节解析请求页的文字层。14 项标准字体与 168 项 CMap 均已内置，构建时逐项核对固定大小与 SHA-256，浏览器按精确名称取用并按需解码、校验；解析期间不调用资源工具，不连接 CDN，也不使用 WASM。
4. 组件提交分页正文；普通 `document_read` 在后续非阻塞调用中返回实际文本。GPT 据此回答，而不是仅看到文件卡片或上传回执。

这里使用浏览器解析，Node 服务不解析 PDF。它是「原文件传入组件，再回传可读正文」，**不是 ChatGPT 原生附件上传**。哈希校验确认源字节一致；服务端校验页码、预算和票据，不能独立证明组件提交的文字语义与 PDF 相符，返回中标记 `text_verification: component_reported`。

原文件分块在末块允许 `next_offset` 为 `null` 或缺省；只有字节范围恰好到达总长度且 `eof: true` 时适用。非末块必须提供正确的下一位置，错误的显式位置仍拒绝。分块 SHA-256、完整原件 SHA-256、长度、顺序、Base64 编码和设备授权校验均保留。旧的 `document_widget_asset` 仍供旧组件兼容，新组件不调用它。

## 首版边界

| 项目 | 限制 |
| --- | --- |
| 格式 | PDF 文字层；不支持 Office、OCR、图像/图表理解或密码输入 |
| 原文件 | 继续遵循 `limits.fileTransferMaxBytes`，默认 4 MiB、最大 7 MiB；不截断文件。放宽此限制需要后续独立改造快照入口 |
| 私有传输 | 每次最多聚合 4 次既有授权读取，回复最多 256 KiB；每次内部读取仍遵守 `fileWidgetChunkMaxBytes` 和路径校验 |
| 有效期与缓存 | 文档最多 5 分钟，且不超过原字节票据期限；最多 16 文档，每文档 16 页请求、1 MiB 文本缓存；原字节共享现有缓存预算 |
| 分页 | 首次 1–3 页，单请求最多 5 页，总页数最多 2000；每页最多 16 KiB UTF-8，单请求最多 64 KiB；省略部分标记 `truncated` |
| 空页 | `text_layer: empty` 表示未取得文字层；不能据此推断页面没有内容，更不能声称读到了扫描图像 |
| 正文省略 | `text_layer: present` 且 `text` 为空、`truncated: true` 表示文本预算已耗尽；不等于没有文字层 |
| 状态查询 | 每个解析任务最多 30 次 pending 观察，建议间隔 2 秒；重叠范围可能共享任务；已就绪结果不被查询限额遮蔽 |
| 浏览器负载 | 首版使用 PDF.js fake worker，解析发生于组件线程；时间预算不能硬中断同步解析，复杂 PDF 仍可能使组件暂时无响应 |

原件读取、提交、旧资源工具访问及缓存正文读取均重新校验设备、工作区身份和路径策略。内置的字体和 CMap 是公开的固定依赖数据，不携带工作区内容或票据。快照表示打开时的原文件，不随后续编辑更新。文档正文是不可信内容，不构成执行命令或扩大权限的授权。

## 验收标准

本地测试覆盖真实 PDF.js 提取合成 PDF、整文件/分块校验、页范围/预算/空文字层、权限变更及严格串行工具调用。真实 ChatGPT 另须回答**提问中没有提供**的 PDF 标题或正文，并核对内容和页码；记录版本、组件状态与普通读取结果。成功打开组件、返回文件名或哈希均不算通过。

合成回传的历史证据见[回传原型](reading-relay-prototype.md)，本地执行结果见[测试说明](testing.md)。

## 维护依赖

PDF.js 主库与 worker 必须保持同一固定版本。升级时同步审查 `document-assets.ts` 的精确资源清单、哈希和预算，并重新构建组件、保留许可及运行真实字体/CMap 回归。182 项资源原字节共 1,940,006 字节，采用原始 Base64 按需解码，不新增浏览器解压 API 依赖。preview.4 的最终 JS 为 4,379,145 字节，HTML 为 4,380,308 字节，均有 5 MiB 构建或返回上限；真实宿主仍需验证扩大后的资源能否加载。解码缓存上限为 1 MiB、32 项，此数不包括脚本字符串、PDF.js 或正在解析的文档所用内存。

preview.6 生成 `dist/src/assets/document-widget-<版本>-<SHA256>.js` 和同目录的 `document-widget-<版本>.json` 清单，不提交生成代码。先完整写入不可变脚本，再原子替换清单；同版本重建也不会读取部分脚本。Windows 短暂共享锁会有界重试，失败时保留旧清单。读取检查文件大小与 SHA-256，`doctor` 同时检查组件；缺失或损坏时报 `DOCUMENT_WIDGET_ASSET_INVALID`，须成功重建后再重启服务。旧版文件保留供现有进程使用。既有原件分块依然经过宿主调度；内置资源不能保证大型文件的分块永不延迟。
