# 后续路线

以 `0.16.0-preview.7` 为当前基线，优先完成可审阅的公开源码、准确的使用说明和真实宿主验收。功能状态以[实施状态](implementation-status.md)为准，本地测试与宿主测试分别记录在[测试说明](testing.md)。

## 当前基线

已实现单文件配置、本地控制中心、命令执行总开关及字段级配置错误定位；`connect` 提供带临时凭据的页面链接。`fs_copy` 支持同一设备的已授权工作区间直接复制，源可只读且不依赖命令执行。生成文件默认入口为 `fs_save_file` / `fs_save_file_status`，旧下载导入和 Base64 回存作为兼容入口保留。

真实 ChatGPT 的 PDF 正文与生成附件保存仍未通过完整端到端验收，不以模拟宿主或本地协议测试代替。跨平台 CI 也需以仓库实际运行结果为准。

## 生成文件回存：先验证宿主文件交接

真实网页测试已遇到 Base64 在到达写入工具前被截断。preview.7 已接入 `getFileDownloadUrl`、组件私有下载地址交接、官方文件对象直传和原件大小/哈希写前校验，用户不手工复制 URL。下一步在真实 ChatGPT 验证当前生成文件的宿主授权与完成回执，并核对本机大小和 SHA-256。模拟宿主的 2,341,397 字节 PNG 验收不能代替这个证据。

验收要分别记录“已有实际文件 ID”“宿主已解析授权引用”“本机已取得完整原件”“目标已保存并验证”。任一步失败都保留实际错误及操作状态，不能改用另一份文件、缩图或扩大下载域名规则。只有完整链路通过后，才把对应宿主来源标注为已验证。

可变小块仅是兼容性改进候选，需先设计每会话/全局块条目预算、重试边界和持久恢复，不作为解决网页大文件中转的主要方案。API 的 Programmatic Tool Calling 也不能直接等同于 ChatGPT 网页插件能力；未经真实宿主验证，不以它替代现有网页方案。官方依据与失败记录见[回存说明](file-writeback.md)。

## 当前：PDF 正文原型

合成文本回传已在一套真实 ChatGPT 连接中连续成功两次；这不等于 PDF 已读通。当前 PDF 原型在浏览器校验完整原字节，使用随构建内置的 PDF.js、字体和 CMap 解析，再经非阻塞分页工具返回文字层。下一关是在真实 ChatGPT 回答合成 PDF 第 1 页和第 4 页中的未知校验内容；通过后再验证真实论文。之后评估大于 7 MiB 的独立快照入口、长文档预算及更复杂字体，不把原型说成原生附件或 OCR 已完成。

## 优先：发布与稳定性

1. 在 GitHub 运行 Windows/Linux/macOS CI，修复实际平台差异，再决定正式版本范围。
2. 在真实 ChatGPT 对话完成设备识别、文本读写/冲突恢复、跨工作区复制、Codex 接续和可选执行的独立验收；核对操作结果，不能只记录工具可见。
3. 改进工具发现失败和连接锁的诊断；避免模型误把“有工具列表”或“隧道在线”当成操作成功。
4. 为本地控制中心补充状态库、备份、作业日志的空间统计；制定保留与安全清理策略，支持预览和范围确认。
5. 完善服务重启时的新请求排空与作业协调；现有活动作业检查不能宣称为原子的全请求排空。

## 暂停：自动原文件附件

本机原文件通过纯 MCP 自动加入 ChatGPT 原生可读附件、浏览器自动化、Actions 公网接口及第三方隧道暂停开发。它们与已实现的“生成文件保存到本机”方向不同：后者沿现有 MCP 连接交接文件引用，本机仅向官方文件主机发起 HTTPS 下载，不需要新增公网监听、域名或证书。暂停路线恢复前需用户重新确定范围，并满足：

- 宿主接口有明确支持依据；
- 在真实 ChatGPT 中对合成文件完成正文问答，而非仅打开组件；
- 不增加未经接受的扩展、云服务或每文件复杂操作；
- 有跨平台配置、权限、重试和失败恢复设计。

本路线不是发布日期或功能承诺。
