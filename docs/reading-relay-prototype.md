# 浏览器内容回传原型

合成探针行为版本：`0.14.0-preview.4`。该版本已在真实 ChatGPT 连续成功两次，只证明合成文本回传。后续 `0.15.0-preview.1` 的 PDF 接入见 [PDF 正文原型](pdf-reading-prototype.md)；原生附件上传仍未实现。

## 为什么先做这一关

[现有项目调研](file-reading-alternatives.md)发现，MCP Apps 官方 PDF 示例让浏览器组件解析原 PDF，再由普通 MCP 工具返回正文/页图像。WebCodex 先验证其中最容易受宿主影响的环节：组件调用和模型工具调用能否完成一次正文传递。

```text
模型 reading_probe_open
  → 立即准备任务并自动显示组件；随机挑战和提交凭据只通过 _meta 交给组件
组件自动 reading_probe_poll
  → 取得已准备的任务；浏览器计算合成文本
组件 reading_probe_submit
  → 服务缓存实际提交的文本
模型 reading_probe_read(relay_id)
  → 立即返回 pending（尚无文本）或 ready（包含实际 text）
  → pending 时释放调用，给组件执行机会，再在限额内取同一个结果
```

没有文件选择、上传、发送按钮，没有新公网地址、扩展、CDN 或模型 API 调用。组件必须保持运行，不能承诺宿主把它完全隐藏。此次探测不读取任何本地文件。

## 实现范围

- `reading_probe_open/read` 是模型工具；`reading_probe_poll/submit` 通过 MCP Apps 和 OpenAI 兼容元数据声明为组件私有工具。工具隐藏不是鉴权，提交仍需独立随机凭据。
- 挑战与凭据不出现在开组件时的普通 `content/structuredContent`。组件自动计算挑战对应文本，普通读取工具只在收到有效提交后返回该文本。
- 状态保存在 App 实例，适配本项目 HTTP 每次 POST 新建 MCP server 的行为。服务只面向单个本地所有者；没有声称提供 ChatGPT 会话身份认证。每个视图的随机凭据限制提交，服务重启会使旧视图失效。
- 默认视图有效期 120 秒，最多 16 个。每次公开读取立即返回状态，不等待组件。最多允许 6 次 pending 观察；第 7 次仍未就绪时返回 `RELAY_READ_LIMIT`，不能用新建探针绕过本次验收失败。ready 缓存在到期前仍可读取。响应给出 `retry_after_ms` 与 `pending_reads_remaining`，模型应给组件执行机会而不是打开另一个阻塞等待工具。
- 任务在 open 时生成，反复读状态不替换任务，也不删除未提交的工作。组件收到任务后提交一次，并等待确认后结束。上述是合成诊断的内部预算，不是文件大小限制。
- 过期、服务端关闭、错误请求标识或不匹配提交均失败；相同已完成请求返回缓存。处理前已经取消的状态读取不消耗预算，也不取消独立的准备任务；读取已返回后取消不会退回预算。关闭组件只停止浏览器操作，服务端缓存到期或服务退出时清理。
- 合成挑战匹配仅帮助检验真实回传路径，不能证明一般文档解析正确，也不是浏览器可信执行证明。

## 真实 ChatGPT 验收

先等已有作业结束，在原隧道窗口正常停止旧服务，再从项目目录运行：

```powershell
node dist/src/cli.js connect
```

本机先 `npm run build`，并在 ChatGPT 应用设置更新工具定义。确认 `system_status` 为 `0.14.0-preview.4` 且可发现 `reading_probe_open/read`。在启用 WebCodex 的新对话发送：

> 使用 WebCodex 验证合成内容回传。先调用 system_status 确认版本为 0.14.0-preview.4，再调用 reading_probe_open，不传参数。用返回的 relay_id 调用 reading_probe_read。若 status=pending，给组件执行时间，按 retry_after_ms 和 pending_reads_remaining 在限额内取同一个结果；不要打开其他等待工具或新建探针。只有 status=ready 时逐字报告 text；不要自己计算、调用私有工具或读取其他文件。遇到错误则报告实际错误码并停止。

通过必须同时具备：组件自动运行、`reading_probe_read` 返回内容、模型准确复述该次不可预知的文本。仅开组件、提交 ACK、模型说“完成”、本地模拟通过都不算真实宿主验收通过。若失败，保留工具错误及组件状态；不要循环重启、上传或把失败改成成功提示。

### 对话声称没有新工具时

先区分应用工具清单和当前对话的可调用工具。开发者模式的官方[刷新流程](https://developers.openai.com/apps-sdk/deploy/connect-chatgpt#refresh-metadata)要求：服务更新后刷新连接元数据，确认清单改变，再新建对话并重新添加该连接。继续旧对话不能用来证明新清单已加载到模型。

1. 在 WebCodex 应用详情核对 `reading_probe_open` 和 `reading_probe_read`。它们是公开工具；`reading_probe_poll/submit` 才是组件私有工具。
2. 清单存在时，用新对话添加 WebCodex 后测试；清单不存在时，先检查是否刷新了正确的连接及其工具元数据。
3. 用 `system_status` 的实际工具结果核对版本；用本机 `diagnostics show` 核对 `tools/list` 和 `reading_probe_*` 记录。模型一句“不可用”没有对应工具错误码，不能当作服务执行失败。
4. 若版本、应用清单、新对话都正确而仍无法调用，保留该宿主发现问题，不以重启、改名或增加相同工具的别名掩盖，也不扩展 PDF 功能。

2026-09-11 已先确认新版本 `system_status` 成功、`tools/list` 正常返回；随后用户成功触发了 `reading_probe_open/read`。工具发现已通过，真实失败点转为下方的调用时序。

### preview.3 的真实失败与 preview.4 修正

真实 ChatGPT + 官方隧道的服务端诊断（北京时间）：

| 事件 | 时间／结果 |
| --- | --- |
| open | 12:11:36.625，成功 |
| 组件资源读取 | 12:11:37.474，成功 |
| 公开 read 开始 | 12:11:37.825 |
| read 结束 | 12:11:45.858，`RELAY_TIMEOUT` |
| 第一次组件 poll | 12:11:45.886，比超时晚 28 毫秒 |
| 组件 poll 总计 | 51 次成功，但原 read 请求已清除，因此一直 idle；没有 submit |

这证明旧设计不适应本次观察到的调度：read 等待期间没有组件请求到达。仅凭服务端记录还不能确定串行化发生在 ChatGPT 还是隧道层。单纯延长超时仍保留同一依赖。

preview.4 改为提前准备、非阻塞取结果，既支持串行处理也支持并发处理；不要求模型读工具占用期间组件必须进入。旧版本资源地址保留有限别名，返回当前组件，避免缓存资源地址直接变成不存在。

本机串行队列回归不等于真实 ChatGPT 成功。若组件只在模型整轮结束后运行，有界状态读取也可能来不及。此时应记录实际失败，再单独验证宿主的继续对话能力；本版不偷偷发送 follow-up 消息，也不声称无需任何宿主配合即可完成。

## 接下来

只有真实宿主回传通过后，才接入完整原 PDF 字节重建与 SHA-256 校验，再由组件内 PDF.js 解析，返回正文与必要页图像。库、worker 和字体需随构建分发。扫描页、中文、图表、公式、大文件和多工作区将分别验收，不能从合成文本成功推导出这些能力已支持。

当前验收结果与阻碍记录在[测试说明](testing.md)。

2026-09-11，用户提供的两次新探针截图均显示 `reading_probe_read.status=ready`，GPT 逐字引用两段不同的组件文本。运行中服务的只读诊断与截图一致：

| 次数 | open（UTC） | 组件 poll | 组件 submit | 后续公开 read |
| --- | --- | --- | --- | --- |
| 1 | 04:30:13.860 | 04:30:16.451 | 04:30:17.540，35 ms | 04:30:20.870，30 ms |
| 2 | 04:31:40.356 | 04:31:41.672 | 04:31:42.737，44 ms | 04:31:46.061，36 ms |

两次另各有一次初始 read；总共 10 次调用成功。诊断不存正文或 ready/pending 值，实际可读文本证据来自截图。成功范围仅为这一套 ChatGPT/隧道环境的合成文本回传，未由此声称 PDF、原生附件或所有宿主都可用。
